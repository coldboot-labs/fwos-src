# fwos-src

Rust sources for first-party appliance programs. Not OCI recipes.

Bootstrap creates the first administrator in durable FWOS-local Identity configuration, separate from network Desired state. The Appliance console and HTTPS UI share credential verification and a source-qualified authorization boundary; v1 implements local accounts only. HTTPS sessions are held in memory: logout revokes them, and a UI restart or appliance reboot invalidates them.

`fwos-fwd-setup` is the Network startup program: it creates `fwd` and `mgmt`, prepares their fixed links and the Host netns connection, and moves Traffic NICs into `fwd` before netd starts. It then exits; netd owns ongoing network policy and does not enter the Host or Management netns.

`fwos-console` is the Appliance console Host program on VGA and serial, and the only operator program there: it offers the Bootstrap console before ownership (Traffic NIC list and temporary `static`, `dhcp`, or `slaac` addressing), then an authenticated v1 recovery menu for status, restoration of the previous Accepted network revision (`restore-previous`), manual Host image rollback (`rollback-image`), and explicit reboot. It works when the UI is unreachable. It takes no arguments and has no configuration, Desired state display, or Host update commands: routine configuration and Host update are in the UI, and the full Appliance CLI is deferred to v2. It is not a Host shell. Network restoration goes through `netd`'s normal apply and recovery transaction; it does not restore older administrator credentials or roll back the Host image. Host image rollback is a request to the Host update program's `rollback` operation: it queues the previous bootc deployment for the next boot, reports what the next boot runs (and any staged update that `bootc rollback` discarded), and requires the explicit `reboot`; requesting it again before the reboot cancels it. It changes only the bootc deployment: after an accepted update the Accepted Desired state stays in effect (restoring a previous network revision is the separate `restore-previous`), and Identity configuration in shared `/var` stays current, so changed passwords and removed accounts are not reverted and Bootstrap is not reopened. Until appliance health has run and exited on a Host update boot, manual rollback is refused, because health owns that rollback. If health exited without accepting the update, a manual rollback is a rejected update: the previous Release restores the pre-update network as after an automatic rollback. The request records only the queued rollback (`host-image-rollback.json`); the previous Release's `fwos-update restore-check` records the outcome at boot, only if that deployment actually booted, so a cancelled or never-activated rollback reports nothing. `last_update` then names the rollback with a `manual` object (`to`, and whether it restores the pre-update network), an optional field that an older Release ignores. `fwos-update` is the Host update program: its controller wraps `bootc` in the Host netns and listens on a unix socket on `/var`. It runs `bootc switch` in a temporary worker (`fwos-update worker`) that joins the `fwd` network namespace, so the registry download and its child processes use the WAN, including an IPv6-only WAN without a delegated prefix. The worker keeps the Host filesystem and deployment state. In a private mount namespace it hides the Host netns systemd-resolved and resolves names with the WAN resolvers netd publishes in `/var/lib/fwos/fwd-resolv.conf`. It configures no interface, route, or firewall policy. `status` reports under `worker_network` where the last worker ran (`controller: host`, `worker: fwd`). Update resolvers come only from WANs: the DNS servers of a WAN DHCPv6 lease (WAN IPv6 mode `dhcpv6`, or a prefix-delegation request) and the RDNSS servers in a WAN's Router Advertisements (modes `slaac` and `dhcpv6`). netd alone merges them into that file. A static WAN supplies none, because Desired state has no DNS server field, and v1 has no DHCPv4 client on a WAN after Bootstrap. The Host netns has no resolver of its own either: no NIC and no systemd-resolved fallback servers. So a registry name needs a WAN that supplies a resolver; without one, staging fails with "no DNS resolver learned from any WAN". IP-literal registries work on any WAN. Only `localhost` and IP-literal registries are used over plain HTTP. netd's `fwos-pull` NAT44 (Host-netns sources via `mgmt`) is no longer the Host update download path; it stays for any other Host-netns IPv4 traffic that leaves through `fwd`. The controller refuses Host update and reboot until Bootstrap completion is durably recorded. The UI's `start_stage` pulls and stages in the background while `status` reports the booted, staged, and rollback deployments, whether a Host image rollback is queued for the next boot, the reboot requirement, and a running or failed staging operation. Staging does not reboot or touch networking, and a registry or download failure leaves no post-update health record, so it is never treated as a failed boot. Staging asks netd to preserve the Accepted network revision (refreshed at the explicit reboot) and records the previous and staged deployments. After the reboot, the new Release is accepted only when the default target is reached, `fwd` and `mgmt` exist, netd reports that it restored Accepted Desired state and the LAN services it requires, and the UI service is running; a running netd alone is not enough, and upstream reachability is not checked, so an unplugged WAN or ISP outage never causes a rollback. Otherwise it rolls back the bootc deployment and reboots without operator acknowledgement. Before netd starts, the previous Release recognizes the return from the update (`fwos-update restore-check`, contract in `src/host_update.rs`). netd first restores its Accepted state as on any boot, then, if the failed Release changed the network, applies the preserved revision through its normal apply transaction as a new Accepted revision; a failure there restores the displaced revision. If the failed Release left Accepted state this Release cannot read, there is no readable revision to retain, so the preserved one becomes the target of netd's interrupted-apply recovery, which applies it behind the forwarding guard before accepting it. A failure of the failed Release's own state at the startup apply still stops netd, as on any boot. Identity configuration is not Desired state and stays current. `status` reports the last post-update health outcome and, after a rollback, netd's network restoration (`restored`, `unchanged`, or `failed` with the reason); the UI shows it. Host update health is separate from Apply confirmation.

Compatibility boundary: preservation and restoration run in the *previous* Release's code, the one being updated from. An update from a Release that predates this behavior preserves and restores no network revision; its rollback relies on the shared Accepted state as before. Because a rollback leaves shared `/var` in place, every Release must keep persistent daemon state and Identity configuration readable by the Release before it: add fields compatibly and make no irreversible v1 migrations (ADR-0046, ADR-0063). This cannot be exercised until a second on-disk format exists; a Release that changes one must test the older Release reading it. `netd` is the built-in addon binary (OCI recipe in `fwos-builtin-addons`). `fwos-ui` is the UI built-in addon binary: HTTPS JSON plus a static JS SPA, unix-socket client of `netd` for network operations and of the Host update program for authenticated Host update status, staging, and explicit reboot. The host image copies binaries at image-build; this tree is not vendored into `fwos-image`.
